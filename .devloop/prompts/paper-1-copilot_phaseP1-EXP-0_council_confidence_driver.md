## 0. Why this cycle exists (post-S-P1-1 reframe)

The original `HANDOFF_2026-05-23.md` line 100 + `PAPER_FRAMING_DECISIONS_2026-05-26.md` D2 hedged the experiment cost as "~$5 of council time, or ~$0 if recoverable from existing NDJSONs (check `out/run1_archive/hl7*` and the `raw` field on `LithrimPipelineBackend._parse`)."

**S-P1-1 verification (2026-05-27, monitor session) confirms the $0 path is unavailable.** Three independent reasons:

1. **No HL7 NDJSON in `out/run1_archive/`.** The archive contains only `scribe_v1`, `scheduling_v1`, `coding_v1`, `triage_v1`. There is no `hl7*` file.
2. **No HL7 NDJSON anywhere in `out/` was produced by `LithrimPipelineBackend`.** The 9 `out/hl7*.ndjson` files are all `MockBackend` / `TunedMockBackend` / `WorstOfBackend` simulations; `out/hl7_adt.live.ndjson` is `LithrimValidateArtifactBackend` (structural-only, no judges).
3. **Even on the 4 packs where `LithrimPipelineBackend` did run, confidence was discarded at parse time.** `JudgeOutput` (`base.py:21-25`) has no `confidence` field; `_parse` (`lithrim_pipeline.py:181-185`) extracts only `judge_role` / `vote` / `findings` from each `judge_votes[i]`. Confirmed against a real live-council row (`out/run1_archive/scheduling_v1.n10.ndjson` row 0) — only verdict + flags present.

The lithrim-backend API contract **does** emit confidence (`lithrim-backend/app/services/pipeline/models.py:28-40`, field `confidence: float = 0.0`). The data exists on the wire; bench just doesn't capture it.

Therefore P1-EXP-0 must:
- (a) extend the bench to capture per-judge confidence at parse time
- (b) re-run the council on `hl7_adt_v1` once (N=1, 40 cases, ~$5)
- (c) aggregate confidence on the silent-confident subset and write the §5 headline measurement

No lithrim-backend change is required.

## 2. Deliverables (file-by-file)

### Deliverable 1 — bench plumbing: capture per-judge confidence

1. **`lithrim_bench/backends/base.py`** — add `confidence: float = 0.0` to `JudgeOutput` dataclass (line 22-25). Default = 0.0 preserves backward compatibility with `MockBackend`/`TunedMockBackend` which don't populate it.

2. **`lithrim_bench/backends/lithrim_pipeline.py`** — in `_parse`, change the `JudgeOutput(...)` construction (lines 181-185) to also pass `confidence=float(jv.get("confidence", 0.0))`.

> **Do NOT also persist `confidence` in `BackendVerdict.raw`.** `raw` is a 5-scalar pin (lines 204-210); the new field belongs on `per_judge`, not `raw`. Keep the existing `raw` schema byte-stable so BRS-0b's §7 snapshot test does not regress.

### Deliverable 2 — live experiment run

3. **`scripts/measure_council_confidence_hl7.py`** — new script. Single purpose: run `LithrimPipelineBackend` on `out/hl7_adt_v1.jsonl` once, with `validator_id=93` (strict HL7 ADT^A04 — caught all 28 defects per `STRICT_HL7_VALIDATOR_2026-05-22.md`), and emit `out/p1_exp_0_council_confidence.ndjson` (one row per case, full `BackendVerdict` JSON including the new `per_judge[*].confidence`).
   - Read API key + org from `.live_env` (mirror `scripts/run_determinism.py:106-119`).
   - Pack a single argparse flag `--n` (default 1) so a future executor can re-run with N=3 if the monitor decides robustness matters.
   - Defaults: `--n 1`, `--validator-id 93`, output to `out/p1_exp_0_council_confidence.ndjson`.
   - Run resilience: per-case try/except so one HTTP failure doesn't abort the sweep; failed rows write `{"case_id": ..., "error": "..."}` and the script exits 0 if ≥ 90% of cases succeeded (38/40), exits 1 otherwise.

### Deliverable 3 — aggregation + writeup

4. **`scripts/analyze_council_confidence.py`** — new script. Reads `out/p1_exp_0_council_confidence.ndjson`, filters the "silent confident certification" subset (`expected_compliance_verdict == "reject"` AND `compliance_verdict == "approve"` AND every `per_judge[*].verdict == "approve"`), and emits:
   - `out/p1_exp_0_council_confidence.summary.json` — per-judge mean/median/p25/p75 confidence on the silent subset; histogram bucketed at 0.1 intervals; counts (total defects, silent subset size, per-judge agreement breakdown).
   - `out/p1_exp_0_council_confidence.summary.md` — human-readable single-page report with the headline sentence drafted for §5: "On the N HL7 ADT^A04 defects that the council unanimously approved, per-judge mean confidence was {policy: X, risk: Y, behavior: Z}; the histogram is concentrated in the [a, b] bucket."

The following are tempting but OUT of scope for this cycle:

- **Extending `scripts/run_determinism.py` to forward `--validator-id`** — `LithrimPipelineBackend` already supports `validator_id` constructor kwarg (`lithrim_pipeline.py:47, 62`); we write a dedicated experiment script instead so the run_determinism shape stays stable. If you genuinely think the extension belongs in `run_determinism.py`, surface in plan-review.
- **Re-running the 4-pack semantic sweep** — out of scope; the §7 numbers stay frozen per BRS-0b.
- **Modifying any paper_draft file other than the new §5** — see Deliverable 4 note.
- **Modifying `BackendVerdict.raw`** — must stay byte-stable for BRS-0b's §7 invariance snapshot. The new field lives on `JudgeOutput`, not `raw`.
- **Modifying any lithrim-backend code** — the API contract already carries confidence. Zero backend changes required.
- **Adding a `confidence` field to `WorstOfBackend` composition logic** — composition operates on verdicts, not confidences. This is a measurement-capture cycle, not a composition-change cycle.
- **Computing aggregate "council confidence" as a single scalar across judges** — per-judge breakdown is the load-bearing observation; an averaged scalar hides the per-judge variance the §5 headline depends on.
- **Drive-by formatting / dependency bumps / "while I was here" edits.**

If something feels load-bearing-but-not-listed, halt and surface it in plan-review.
