## 0. The gap (S-BS-103) — CORRECTED root cause

Live dogfooding (DOGFOOD-1, 2026-06-09) found: selecting an imported case in the rail and asking the chat to "review this case" showed **`ws0_default`**'s agent/runs/audit, not the selected case. **The original diagnosis (shell doesn't pass the agent) is WRONG — re-grepping proved the binding chain is already wired:** `app.jsx:183` passes `agent={activeAgent}` → `panes.jsx:138` `chatStream({message, agent, history})` → `bff.js:182` POSTs `agent` in the body → `app.py:1393` `chat_endpoint` calls `_build_tool_context(req.agent)`.

**The actual root cause is in the BFF agent loop:**
1. **`_SYSTEM_PROMPT` (`loop.py:28`) is a static string that never names the active agent** — so the LLM has no idea the current evaluation is the rail-selected case.
2. **The agent-scoped tools take the LLM's parameter, not `req_agent`:** `_get_agent(name)` (`app.py:1200`) and `_run_eval_replay(agent)` (`:1189`) use whatever the model passes; with no active-agent context, the model defaults to `"ws0_default"`. (Contrast `_get_judge` `:1186` which correctly uses `agent=req_agent`.) The `ToolContext` already carries `default_agent=req_agent` (`:1365`) — but these closures don't read it.

**Goal:** make the chat loop operate on the **active agent (`req_agent`)** by default — so "review this case / show this case" targets the rail-selected case (`get_agent`/`run_eval`/`review_runs`), which is what enables *demoing, from chat, the case you're actually evaluating*. **A-SAFE is non-negotiable:** add NO paid path — the chat stays replay-only/`$0`; only the human's in-DOM cost-confirm fires a paid run.
