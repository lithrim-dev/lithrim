## 0. The two seams — verbatim evidence (re-verify on read; halt on drift)

### S-BS-149 (med) — rail ↔ active-agent divergence

The rail derives the plan from the shell's `activeAgent`; the chat shepherd resolves its OWN
agent. In a workspace that does not contain `ws0_default` they disagree on *which agent is
being set up* — the rail shows a blank "0/5" while the shepherd operates a configured agent.

**Shell side — `activeAgent` defaults to `ws0_default`, NO coercion against the workspace agent list:**
```jsx
// apps/shell/src/app.jsx:188-191
const [activeAgent, setActiveAgent] = useState(() => {
  try { return new URLSearchParams(window.location.search).get("agent") || "ws0_default"; }
  catch { return "ws0_default"; }
});
```
```jsx
// apps/shell/src/app.jsx:235 — the rail feeds getAgent(activeAgent); a 404 → null → blank plan
getAgent(activeAgent).catch(() => null),
// apps/shell/src/app.jsx:355
const journey = deriveSteps(agentCfg, runs, activeAgent, runResult);
```

**Chat side — `_resolve_chat_agent` COERCES an absent agent to `names[0]`:**
```python
# apps/bff/app.py:1479-1483
if req_agent in names:
    return req_agent  # GUARDRAIL: honor a valid (incl. explicitly-targeted) agent
if names:
    return names[0]  # coerce an invalid/stale arg to the active workspace's first agent
return req_agent  # no agents on disk — keep the ask so the loop surfaces the honest 404
```

**CONFIRMED divergence:** workspace agents `["eval-1","snomed-demo"]`, shell `activeAgent="ws0_default"`
→ rail does `getAgent("ws0_default")` → 404 → `agentCfg=null` → all-`todo` "0/5", Domain NOW;
shepherd does `_resolve_chat_agent("ws0_default")` → `"eval-1"` → reads/leads eval-1's real state.
The rail and the shepherd describe different agents in the same view. **CONFIRMED.**

## 2. Deliverables (work-items; file paths are starting points — confirm on read)

### W1 — Converge the rail onto the SAME agent the shepherd configures (closes S-BS-149)

**Approach (chosen): shell-side coercion that MIRRORS `_resolve_chat_agent`.** When the workspace's
agent list is known (`refreshAgents` → `agents`), if `activeAgent` is NOT in `agents`, coerce
`setActiveAgent(agents[0])`. A valid `activeAgent` (incl. a valid `?agent=` deep link) is HONORED
verbatim — same guardrail as the BFF. This makes the shell pick exactly what `_resolve_chat_agent`
picks (`names[0]`), so rail-derivation and the shepherd operate on one agent.

- Fire the coercion where the agent list resolves: on mount/load and on **workspace switch** (the
  workspace switch is when the agent set changes out from under a stale `activeAgent`). Keep it idempotent.
- **Watch the documented remount race** (`app.jsx:186-187`: changing `activeAgent` remounts `CenterPane`
  via `sessionKey`/`key`). The coercion must settle to a stable agent (no flip-flop, no chat-remount
  loop). If coercing risks a loop, gate it to "only when `agents` is non-empty AND `activeAgent ∉ agents`".
- **Single-source-of-truth note:** this is a thin mirror of the BFF contract (`absent → names[0]`,
  `present → honor`). The two MUST stay in sync. Add the W3 test that pins the shell coercion to that
  exact contract so a future BFF change can't silently desync. (If plan-review finds a cleaner
  single-source option — e.g. the chat SSE echoing its resolved agent so the shell syncs to it — raise
  it; but do not add round-trip plumbing that leaves the *first* render (pre-chat) still divergent.
  The rail must be correct before the first chat turn, which favors shell-side coercion.)
- Files: `apps/shell/src/app.jsx` (the coercion, near `refreshAgents`/the workspace-switch handler).
  `journey.js` stays PURE — do not move resolution into it.

### W2 — One-step-and-wait: make pacing real (closes S-BS-150)

Two layers; **W2b is the substantive fix**, W2a is the cheap reinforcement.

**W2a (prompt) — tighten + foreground the one-step rule in `_SHEPHERD_STANZA`** (`loop.py:145-170`):
- Make the "exactly ONE proposal per turn, then STOP and wait for the human's Save" rule imperative
  and prominent (not buried mid-stanza). State explicitly: do NOT chain multiple authoring proposals
  in one turn; after surfacing one save-pending card, end the turn and wait.
- Preserve the SUPERSET property: the base persona + the HONESTY contract + the active-agent naming +
  the "degrade to operator posture when complete" clause stay intact (the back-compat test still passes).

**W2b (mechanical) — an additive turn-scoped pacing hook capping STEP-PROPOSING tools to 1/turn:**
- In `_build_options`, create a fresh turn-local counter (closure/dict) and register a SECOND
  `PreToolUse` hook alongside `_deny_non_lithrim` (do NOT modify the deny hook). The pacing hook:
  - counts only **step-proposing WRITE tools** — the ones that surface a save-pending editor card
    (e.g. author/put judge, author/put flag, add_grounding_contract, …). **READ tools
    (get_agent / get_judge / review_runs) and the look/teach moves (show_case, focus_artifact) are
    FREE and never counted** — the stanza explicitly wants the start-of-turn live reads.
  - allows the 1st step-proposing tool; **denies the 2nd+** in the same turn with a polite reason
    instructing the agent to surface the one card it already proposed and wait for the human's Save
    before proposing the next step. (A `PreToolUse` deny prevents the audited write from running, so
    no second card is fabricated and nothing is half-committed.)
  - fails-closed-safe: any error in the pacing hook must not open a tool (and must never shadow the
    deny hook's decision). Order so the safety deny still governs.
- **Enumerate the tool taxonomy from `tools.py` in plan-review** (WRITE/propose vs READ vs look). The
  cap is **per step-proposing write**, == "one step per turn". **OPEN QUESTION for plan-review:** does
  ANY single journey step legitimately need >1 write tool in one turn? If yes, the cap must key on the
  *step*, not the raw write count — confirm against the live tools before coding. If every step == one
  write, the simple 1-write cap is correct.
- `tools.py` stays **byte-stable** — the cap reads tool *names* in the hook; it does not edit the tools.

> If W2b proves to over-engineer at plan-review (e.g. the SDK can't cleanly surface tool_name to the
> hook on this version, or a step genuinely needs multiple writes), fall back to **W2a-only** for this
> cycle and SPLIT W2b to a precondition-gated follow-on — say so explicitly, do not silently drop it.
