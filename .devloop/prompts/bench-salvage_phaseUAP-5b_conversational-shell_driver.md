## 0. Why this phase (the capstone — the conversation IS the audit log)

UAP-1..4 built the product as a **tools surface** (the BFF ops) + an **output surface** (the gen-UI `tool-<name>` registry). UAP-5b is the **driver** that connects an utterance → those tools → those cards: **the Claude Agent SDK hosted in the BFF**, the BFF ops wrapped as in-process SDK-MCP tools, a multi-turn author→process→review loop streamed (SSE) to the shell chat pane, tool-results adapted to the gen-UI parts the shell already renders. Every tool-call is a config write → already audited (R0): **the conversation IS the audit log.**

**Right-sized (the UAP-4 anti-over-engineering lesson):** the user's vision is *"complete the whole journey from scratch by talking."* That's the **target / A-LIVE direction** — but this cycle ships the **SPINE + a 2-3 tool core** (prove the loop end-to-end: talk → audited write → card renders → run), and the **full Domain→Judge→Flag→Run→Review-from-a-blank-agent loop is a fast-follow (UAP-5c)**. The tool surface already exists, so the spine work is the loop + SSE + the parts-adapter + thin per-tool wrappers — *not* new ops; each additional tool then grows the journey cheaply.

**The one de-risk (D0, GATING):** `claude_agent_sdk` is **not installed** and there is **no `[agent]` extra**. The whole approach (OQ-6=B + the BYO-Claude licensing guardrail) rests on the SDK supporting **local-CLI / BYO-Claude auth** (the desktop subscription, no API key) — the same trust wedge the zyng `ClaudeCliClient` proved for the single-shot R10 path. Prove that first.
