## 0. Why this phase (the third leg of author→process→OPTIMIZE)

UAP-2 authors a judge; UAP-3 runs it; **UAP-4 lets an SME TUNE it in the UI and see — honestly, LIVE — whether it got better.** This is R5 realizing `SPEC_CALIBRATION_TRAINER.md` — *"calibration is the product… a trainer, not a demo"* — the **"pull a lever → re-run → diff the number"** loop that closes the "who calibrates? — the SME, in the UI" gap.

**v3 scope (right-sized from the live `:5180` look) = the demonstrable-live optimize→honest-Δ loop, embedded in JudgeEditor:**

```
   assign/edit the lens  ──►  OPTIMIZE (paid)  ──►  honest held-out Δ
        (UAP-2, $0)            in-DOM cost modal     (precision/recall before→after,
                                                      WIN-OR-LOSS, a NET-NEW Δ render)
```

**Why this exact cut (the anti-over-engineering reassessment):** a live browser pass confirmed the Shell is already a mature author→process→audit flow. The **re-run/verdict surface already exists** (the `Run evaluation` card + `Run history (25)` + the in_process paid mode). And optimize's held-out Δ is **NEGATIVE today** (S-BS-49), so a bind→re-run "watch the verdict improve" leg **cannot be demonstrated live** until optimize wins. Building the bind-persistence backend now = machinery for a dark path → **SPLIT to UAP-4-opt** (cheap to add once a win exists, because the Run surface is already built). What's genuinely net-new, small, and demonstrable-live is the **optimize→honest-Δ render** — that is UAP-4.

**The engine EXISTS** (`judge_optimize.py`, WS-6c-DSPy-3b): `run_optimize` (cost-gated, returns the held-out Δ), `compile_judge` (BootstrapFewShot), `evaluate_program`. So UAP-4 is **a BFF route + a small Δ render in JudgeEditor + a gate-fix attempt** — no new ML, no round-trip backend.

**⚠️ The load-bearing honesty:** the WS-6c-DSPy-3b held-out Δ was **NEGATIVE** (precision 0.71→0.44) — **S-BS-49:** the exact-accept gate harvests only the already-perfect *silent* demos → 0 positive exemplars → over-fire. And `SPEC_CALIBRATION_TRAINER §4.1`: the prompt lever is **non-monotonic**. **The user has decided a live, honestly-rendered LOSS IS the delivered experience** (R1). D3 actively *attempts* a win (lead lever: corpus-widening), but **a manufactured win = FAIL** (the `run_optimize` contract: *"a measured Δ — including ≤0 — is the loop-closure; the gate is never loosened"*).
