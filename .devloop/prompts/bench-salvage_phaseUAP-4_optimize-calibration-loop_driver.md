## 0. Why this phase (the third leg of author→process→OPTIMIZE)

UAP-2 authors a judge; UAP-3 runs it; **UAP-4 lets an SME TUNE it in the UI and see — honestly — whether it got better.** This is R5: `POST /v1/judges/{role}/optimize` over the DSPy optimizer, surfacing a **measured held-out Δ** in the shell. It realizes `SPEC_CALIBRATION_TRAINER.md` — *"calibration is the product… a trainer, not a demo"* — the **"pull a lever → re-run → diff the number"** loop that closes the "who calibrates? — the SME, in the UI" gap.

**The engine EXISTS** (`judge_optimize.py`, WS-6c-DSPy-3b): `run_optimize` (cost-gated, returns the held-out Δ), `compile_judge` (BootstrapFewShot), `evaluate_program`, `_serialize_demos`. So UAP-4 is **surface + a gate fix**, not new ML.

**⚠️ The load-bearing honesty (read the WS-6c-DSPy-3b critique):** the optimizer's held-out Δ was **NEGATIVE** (precision 0.71→0.44) — **S-BS-49:** the exact-accept gate harvests only the already-perfect *silent* demos → 0 positive exemplars → the compiled judge over-fires. And `SPEC_CALIBRATION_TRAINER §4.1`: the prompt lever is **non-monotonic**. So "optimize" does NOT reliably improve a judge yet. **UAP-4 is part DSPy-quality research (make optimize win), part UI (surface the honest Δ).** The `run_optimize` contract is explicit: *"a measured Δ — including ≤0 — is the loop-closure; the gate is never loosened to manufacture a win."* **Honor that. A manufactured win is a FAIL** (the UAP-3b-2 live-attestation posture, applied to the optimizer).
