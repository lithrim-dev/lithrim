## 0. Why this cycle exists (one paragraph)

WS-0 proved the live grading spine; WS-1 lifted the run into a SQLite config
plane (`Agent` + `EvalProfile {judges, council_config, ontology_ref,
ontology_path, tools, kb_bindings, severity_map_ref}`) and an ontology data
model — but the `council_config` and `ontology` in the eval-profile are
**stored only** (S-BS-6 ratified, injection deferred). The live
`:8002 /v1/pipeline/evaluate` call in `grade_live` still sends a fixed body
and the backend council still reads its config from disk-prompts +
`COMPLIANCE_COUNCIL_VERSION` env. **WS-2 closes the loop:** make
`PipelineRequest` accept the Agent's `council_config` + `ontology` as
**Optional, additive, backward-compatible** fields, thread them into the
council's prompt build + model selection + tier/owner/question lookup, and have
the harness inject the stored SQLite config into the evaluate call. After WS-2,
a new domain is a new ontology row that drives the live council — not a backend
code change. **Deliverable-0** lands the S-BS-10 decision first
(snapshot-authoritative flag membership + a lint gate), harness-only, so the
ontology that drives live grading is gradeable-by-construction before it is
injected.
