## 0. What this cycle is (the one-paragraph frame)

The DSPy judge **loop** is: judges-as-modules (WS-6c-DSPy, done) → a bench-accept **metric** (`make_judge_metric`, done) → a by-construction **labeled corpus** (`judge_calib_v1.jsonl`, WS-6c-DSPy-3a, done) → **optimize** a judge against the metric on the corpus → **measure** compiled-vs-baseline on a held-out split → show the compiled judge can be **bound back** into the production trio. The first three exist; this cycle adds the last three. "Complete the loop" = demonstrate, end-to-end on **one judge** (`risk_judge`, the rebuilt-first judge with the most positives — `WRONG_DOSAGE`×8 + `MISSED_ESCALATION`×6), that `BootstrapFewShot` compiles a judge whose held-out score is **measured** against the un-compiled baseline, and that the compiled demos can be loaded into a `Judge`. The trio (policy + faithfulness) is **more coverage, not more loop** — offered as an explicit optional same-cycle extension under a second cost-go, not the default.

**The load-bearing invariant (whole DSPy track):** DSPy lives ABOVE the per-judge seam. The ported consensus IP (`compliance_council._apply_consensus`, tier tables, owner-gating, Tier-1 never-events, the llama-veto, None-confidence tolerance) is **byte-frozen** — `git diff` on `compliance_council.py` MUST be **0 lines** this cycle (A1). Optimizing a judge prompt can never weaken a Tier-1 rule, because the rule lives below this layer (`RECOMPOSITION_PLAN_ws6.md` §6).

## 2. Deliverables (file-by-file)

1. **`lithrim_bench/runtime/council/judge_optimize.py`** *(new module — the loop's missing piece; `dspy` imported lazily, mirroring `judges_dspy.py`/`ab_harness.py`)*
   - **`JudgeProgram` (a `dspy.Module`)** — the **compilable view** of a judge: a thin module whose `forward(transcript, artifact, role_key_questions, taxonomy_context)` calls one `dspy.Predict(JudgeSignature)` and returns its `dspy.Prediction(decision=, findings=)`. This is the thing `BootstrapFewShot` compiles (it traces the inner `dspy.Predict` and attaches few-shot demos). It is **separate from and additive to** `Judge` — `Judge.forward`'s seam-dict return stays frozen (A1). Both wrap the **same** `JudgeSignature`, so demos compiled on `JudgeProgram` transfer to `Judge.predict`.
   - **`build_examples(rows, *, role) -> list[dspy.Example]`** — project corpus rows for `role` into DSPy examples: `dspy.Example(transcript=row["transcript"], artifact=_artifact_text(row), role_key_questions=load_role_prompt(role), taxonomy_context=default_taxonomy_context(), expected_safety_flags=row["expected_safety_flags"]).with_inputs("transcript","artifact","role_key_questions","taxonomy_context")`. Keep the **pure row→dict projection** in a separate helper (`_example_fields(row, role) -> dict`) so it is testable offline without `dspy`. (Reuse `ab_harness._artifact_text`; do not re-implement.)
   - **`load_corpus(path, *, split=None) -> list[dict]`** — read `judge_calib_v1.jsonl`, optionally filter by `split` (`"calibration"` / `"test"`). No `dspy` needed.
   - **`compile_judge(role, trainset, *, lm=None, predictor=None, max_bootstrapped_demos=4, max_labeled_demos=16) -> JudgeProgram`** — build a `JudgeProgram` (bind `lm` live via `build_judge_lm(role)`, or inject `predictor` offline), then `dspy.teleprompt.BootstrapFewShot(metric=make_judge_metric(lens_codes=LENS_BY_ROLE[role], co_raise_aware=True), max_bootstrapped_demos=…, max_labeled_demos=…).compile(program, trainset=trainset)`. Return the compiled program.
   - **`evaluate_program(program_or_judge, cases, *, role, co_raise_aware=True) -> dict`** — wrap the program/judge as `run_judge(case)` and return `score_judge(run_judge, cases, lens_codes=LENS_BY_ROLE[role], co_raise_aware=co_raise_aware)`. Used identically for the **baseline** (un-compiled) and the **compiled** program → the held-out Δ.
   - **`bind_compiled_demos(judge, program) -> Judge`** — copy `program.predict.demos` (the compiled few-shot demos) onto a `Judge`'s `predict.demos`, proving the loop closes (the optimized judge can become the production judge). **Mechanism + a test only this cycle** — do NOT change `build_trio` to load demos by default (that is a production-behavior change → follow-up; see §4).
   - **`run_optimize(role="risk_judge", *, corpus_path, confirm_cost=False, out_dir) -> dict`** — the **paid** entrypoint. Refuses without `confirm_cost=True` (copy `ab_harness.run_live:227`'s `RuntimeError`). Steps: load corpus → `train=split"calibration"`, `heldout=split"test"` (both lens-filtered to cases relevant to `role` — a case with no in-lens label AND a clean-negative still counts as a held-out negative; keep clean-negatives in held-out, they measure over-fire) → `baseline = evaluate_program(JudgeProgram(live), heldout)` → `compiled = compile_judge(role, train, lm=…)` → `optimized = evaluate_program(compiled, heldout)` → persist compiled demos + both score dicts to `out_dir`. Returns `{role, n_train, n_heldout, baseline, optimized, delta}`.

2. **`scripts/optimize_judge.py`** *(new thin CLI — the live runner, like the DSPy-2-live run script)*
   - `argparse`: `--role` (default `risk_judge`), `--corpus` (default `examples/judge_calib_v1.jsonl`), `--confirm-cost` (default False), `--smoke` (compile/eval on **2 cases only** for the per-call cost check), `--out` (default `docs/research/`). Calls `run_optimize`. Prints the held-out Δ table. **No Azure call unless `--confirm-cost`.**
   - No service autostart; Azure is reached directly via the council `settings`/`dspy.LM` (the user owns `../lithrim-backend/.env`), exactly as DSPy-2-live did — NOT `:8002`.

3. **`lithrim_bench/runtime/council/tests/test_judge_optimize.py`** *(new — all $0, deterministic, default-deps where possible)*
   - **Offline projection:** `_example_fields(row, role)` builds the right input dict from a fixtured corpus row (default deps, no `dspy`).
   - **Offline eval-Δ:** with two **injected fake predictors** (a "baseline" that raises an extra over-fire code + a "compiled" that raises exactly the in-lens label), assert `evaluate_program` returns a higher `graded`/`precision` for the compiled arm — i.e. the Δ-measurement logic is correct (mirror `ab_harness` offline-structural; $0, no network).
   - **Offline demo-binding:** `bind_compiled_demos` copies demos onto a `Judge` (use a stub `program` exposing `.predict.demos`); assert the `Judge` carries them. Structural, no live call.
   - **Live compile/eval:** `importorskip("dspy")` + env-gate (`LITHRIM_LLM_PROVIDER=azure` + `AZURE_OPENAI_*`, the `test_live_smoke.py` gate) → **skips $0 by default**, runs only under the same env as the live smoke. Asserts a compiled program is produced and held-out scoring returns the dict shape.

4. **`docs/research/REPORT_dspy3b_optimizer_2026-06-03.md`** *(new — the loop-closure record)* + the persisted compiled-demos snapshot + the baseline/optimized held-out score dicts under `docs/research/` (NOT `out/` — `out/` is gitignored per WS-6a). The REPORT states the held-out Δ for `risk_judge`, the train/held-out N, the compile config (`max_bootstrapped_demos`/`max_labeled_demos`), and **the 4 mandatory caveats** (small-N; precision is the co-raise-aware figure; transcript-only blind spot; **NOT a paper claim**). If the Δ is ≤0 (optimization did not help on this corpus), that is a **valid, reportable loop-closure** — the loop is "complete" when it is *measured*, not when it *wins*.
