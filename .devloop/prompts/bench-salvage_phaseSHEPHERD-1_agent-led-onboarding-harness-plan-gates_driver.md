## 0. The vision + the two locked decisions

**User vision (2026-06-15):** *"a Claude Desktop / Claude-Code-like harness experience for EVALs — people talk to a smart Lithrim Agent that shepherds them through their use cases on the platform."*

The shift: today the conversational agent is **reactive** (answers one message at a time; the chat loop is stateless per turn, history-replayed — S-BS-87). The shepherd is **proactive** — it owns a *plan* for the user's eval, leads them step-by-step, proposes each action, and the human steers/approves.

**User decisions (AskUserQuestion, 2026-06-15):**
- **First journey = New-eval onboarding from scratch.** Empty state → pick/author a domain → author judges + flags → load cases → run → see verdict. (The existing SETUP JOURNEY rail, made agent-led.)
- **Autonomy = Plan + approval gates (Claude-Code style).** The agent owns a VISIBLE plan/checklist, leads step-by-step, and PROPOSES each write for the human's approval before it commits.

**Why this is mostly COMPOSE (recon ledger, 2026-06-15):**
- REUSE: cross-turn memory (S-BS-87 history-replay, proven), the 16 SDK-MCP tools, the config-plane + per-tool audit, the gen-UI registry, the 3-pane shell.
- The save-pending editor cards you already see live (`Agent · eval-1`, `Judge · risk_judge` with Save buttons) ARE the approval-gate pattern — the agent proposes, the human Saves. SHEPHERD-1 formalizes + wires it to the plan.
- NET-NEW: the rail wired to real state (the *plan*), a proactive plan-aware prompt, and the save→advance loop.

## 2. Deliverables (work-items; file paths are starting points — confirm on read)

### W1 — The live plan surface: wire the SETUP JOURNEY rail to real config state
- Today `STEPS` (`apps/shell/src/data.jsx`) is hardcoded all-`todo`, the "4 / 6" counter is a literal string, and `panes.jsx` renders it static. Make each step's `state` (`done`/`active`/`todo`) **derive from the active agent's config + run history**:
  - **Domain** done ⟺ an active agent exists with an `ontology_ref` set.
  - **Judges** done ⟺ the agent's judge roster is non-empty.
  - **Ground truth** done ⟺ ≥1 grounding contract present (EvalProfile tools/grounding_checks).
  - **Knowledge base** (optional) done ⟺ `kb_bindings` present; never blocks progress.
  - **Run** done ⟺ ≥1 run in history (`GET /v1/runs`).
  - **Review** done ⟺ a run exists/has been opened.
- Derive `active` = the first incomplete required step; compute the "N / 6" from completed. Source data: `GET /v1/agent` + `GET /v1/runs` (already in `app.py`). Keep the derivation a small pure helper (testable). This rail IS the shepherd's plan surface.
- Files: `apps/shell/src/data.jsx` (step model), `apps/shell/src/panes.jsx` (rail render + the data wiring), possibly a `apps/shell/src/journey.js` helper.

### W2 — The shepherd brain: a proactive, plan-aware system-prompt mode
- Add a **shepherd variant** of `_system_prompt` (`apps/bff/agent/loop.py`) — or extend the existing prompt with a plan-aware stanza — so the agent:
  - KNOWS the journey order (Domain → Judges → Ground truth → KB → Run → Review) and, from the live reads it already does (`get_agent`, `review_runs`), identifies the **current incomplete step**.
  - On a fresh/empty eval (agent with no judges) OPENS with guidance — e.g. *"Let's set up your first evaluation. What kind of AI output do you want to grade?"* — and LEADS the next step rather than waiting.
  - After each step, proactively proposes the next (one step at a time; do not dump the whole journey).
  - Stays grounded: never claims a capability it lacks; proposes, never fabricates (reuse the existing no-hallucination posture; the full `capabilities_v1.json` guardrail is SHEPHERD-2, but do not regress honesty).
- Keep it a BOUNDED prompt change. If a `mode` flag is needed (operate-vs-shepherd), thread it minimally through the chat request → `ToolContext`; default behavior must stay back-compatible for non-onboarding chats.

### W3 — The approval-gate save→advance loop
- Formalize propose→approve→advance using what already exists:
  - The agent PROPOSES a write as a save-pending editor card (already happens — CONV-UX-1 confirmed `Agent`/`Judge` editors render with a Save button; the actual audited `PUT` is the human's Save). The agent NEVER auto-commits a step.
  - On the human's Save (the existing audited write), the rail (W1) re-derives → the step flips to `done`, and the shepherd (W2) acknowledges + proposes the next step.
- Wire the loop: save (audited write) → rail re-derive (W1 helper) → the agent's next-turn plan-awareness (W2, via the live read). No server-side session state — use the existing history-replay + live config reads (S-BS-87). Confirm the existing editor cards already emit on the save path; if a small shell event is needed to trigger the rail re-derive on save, add it minimally.

### W4 — Adaptive entry (replace the static empty-state with shepherd entry)
- The empty-state chips today are static (`"Create a risk judge / Add a safety flag / Run a $0 replay"`, `panes.jsx`). Make the entry **shepherd-aware**: an empty eval offers a primary **"Start guided setup"** (kicks off the shepherd) + the next incomplete step; a partial eval offers the next step. Keep it a fill-the-composer or a single send (no surprise paid actions). Small, within the navy/coral/Geist language, hand-compact JSX, no prettier.

### W5 — Tests (hermetic, network-free)
- W1: the rail-derivation helper over config fixtures — empty agent → all `todo` + Domain `active`; agent with judges → Judges `done`, Ground truth `active`; with a run in history → Run `done`; the "N/6" count. (Vitest for the shell helper; or a Python test if the derivation lives BFF-side.)
- W2: assert the shepherd prompt carries plan-awareness (the journey order + a "propose the next incomplete step" instruction) at the prompt-construction layer; assert back-compat (non-shepherd chats unchanged).
- W3: the save→advance derivation (a fixture where saving a judge flips Judges `done`).
- Keep offline; `importorskip("claude_agent_sdk")` for any `[agent]`-gated loop assertion, per the existing pattern.
