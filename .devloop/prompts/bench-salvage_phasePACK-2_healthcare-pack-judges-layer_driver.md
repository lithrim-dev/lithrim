## 0. Why this cut (and why ONLY the prompts, not the roster)

PACK-1 relocated the ontology + taxonomy (the "what is true" contract). Layer-2 is the
**judges**. The clinical judge *content* that is domain-specific is the **role prompts**:
`lithrim_bench/runtime/council/council_roles/{risk,policy,faithfulness,behavior,source_message}_judge.txt`
— the clinical-safety / HIPAA / fidelity prose each judge votes under. These are the clean
analogue of `clinical_v1.json`: domain content sitting above the consensus machinery.

**But layer-2 is NOT "the same shape as PACK-1," and here is exactly why.** The role prompts
are read by **two** paths:

1. `lithrim_bench/runtime/council/judge_assignment.py:25` `_ROLE_PROMPTS_DIR` — the
   **council-LIGHT** path (`load_role_prompt`/`render_role_questions`, re-exported into
   `judges_dspy.build_trio` + the optimizer + the BFF `$0` prompt preview). No `openai`/`dspy`
   import. **Above the frozen seam — freely movable.**
2. `lithrim_bench/runtime/council/compliance_council.py:470` `_ROLE_PROMPTS_DIR` — the
   **FROZEN live council** globs the prompt files *itself* (`_load_role_prompts`, `:522-528`,
   `cls._ROLE_PROMPTS_DIR.glob("*.txt")`). **Inside the frozen seam.**

In PACK-1 the frozen council carried its own *value-copy* of the codes (`KNOWN_TAXONOMY_CODES`),
so the gate AST-parsed them read-only and the council never touched the moved file (D-A:
`compliance_council.py` byte-untouched). **Here the frozen council reads the prompt *files* at
runtime** — so physically moving them to `packs/healthcare/` breaks the live council unless its
`:470` path moves too. There is no clean "2a above the seam."

**The resolution (user-authorized 2026-06-09): the surgical carve-out.** Relocate the prompts;
point BOTH `_ROLE_PROMPTS_DIR` constants at the pack via a resolver; the one frozen-file edit
(`compliance_council.py:470`) is a **path-only, behavior-preserving carve-out** guarded by a
freeze proving everything else in `compliance_council.py` is byte-identical. The consensus
engine, the owners (`_TIER1_OWNERS` `:233-262`), the CouncilModel roster (`:485-516`), and
`KNOWN_TAXONOMY_CODES` are untouched. **Un-hardcoding the roster/lenses/owners so the council
reads its roster FROM the pack is layer-2b — still deferred** behind explicit authorization.
