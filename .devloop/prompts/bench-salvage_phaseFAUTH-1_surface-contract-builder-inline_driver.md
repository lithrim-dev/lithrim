## 0. What this cycle is (and what it is NOT)

**The goal (SPEC_FLAG_AUTHORING_SELF_SERVE §4 step 3 + §6 G1):** make the conversation *hand the
physician the interactive contract-authoring widget inline* — exactly the way `get_judge` surfaces
the `JudgeEditor` card inline — so a non-coder authors a grounding `verification_contract` by
*filling a card in the chat*, not by the agent silently composing JSON and not by being sent to the
side pane.

**Today (CONFIRMED, the gap):** the only way the conversation touches a grounding contract is
`add_grounding_contract` — the *agent composes* `(flag_code, contract_type, params)` and persists it,
then emits the **read-only** `flag_editor` card (`adapter.py:73-76`, `tools.py:577`). The interactive
`ContractBuilder` widget EXISTS and already persists via the same audited path
(`ContractBuilder.jsx:62-72` → `putGroundingContract`), but it is **never surfaced inline by the
agent** — it lives only in the pane. So the human-authored, fill-the-card-in-chat loop the spec
describes does not exist.

**This cycle = the smallest demonstrable cut:** a $0 SURFACE tool that emits the `ContractBuilder`
INPUT widget inline, seeded with the in-context `flag_code` + agent, so the human fills it and the
widget's existing `putGroundingContract` save (the audited write) persists it. **No new write path,
no new executor, no assist wiring, no new floor** — just surfacing the existing input widget in the
conversation. The mirror is `get_judge` → `judge_part` → `JudgeEditor` (a $0 surface tool that emits
an interactive editor; the *human's* Save is the write).

**NOT this cycle** (later FAUTH phases — see §4): the assist→params wiring (FAUTH-3/G2), the
contract-type↔executor alignment + the registration gate (FAUTH-2/G3), the presence floor
NARR-FLOOR-1 (FAUTH-4/G4), the evidence connector (FAUTH-6/G6).
